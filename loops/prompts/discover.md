## 観点が `user-voice` のとき（この節は該当する回だけ読んでください）

他の観点はコードを読みますが、**この観点だけは本番の利用者の投稿を読みます。**

- 本番サイト: {{PROD_SITE_URL}}
- 本番 API: {{PROD_API_URL}}

このサービスは「困りごとを投稿する」場所なので、**利用者はこのシステム自身への
不満もそこに投稿します。** それを GitHub Issue に転記するのがこの観点の仕事です。

### 手順

1. **全件取る。** `curl -s "{{PROD_API_URL}}/issues?limit=100"` （レスポンスは `data` 配列）
2. **システムへの声かどうかを判定する。**
3. **すでに転記済みでないか確認する。**
4. **すでに直っていないか確認する。**
5. 残ったものを GitHub Issue にする。

### 2. の判定について

「このサイトが」「このシステムに対する Issue です」のような直接の言及は分かりやすい
ですが、**それだけを拾うと取りこぼします。** 実際にあった例:

| 投稿 | 判定 |
|---|---|
| 「このシステムに対するIssueです 名前を出したのに匿名扱いされる」 | システムへの声（明示） |
| 「起票するときに位置情報が必須なのをやめてほしい」 | **システムへの声**（明示はないが機能への要望） |
| 「このサイトですが、画像がまったくないので殺風景」 | システムへの声 |
| 「隣の空き地の草が伸びてひどい」 | 違う（本来の困りごと） |
| 「ベルが水をこぼす」 | 違う |

**判断に迷ったら転記しないでください。** 利用者の本来の困りごとを開発の Issue に
変えてしまうのは、このサービスの趣旨を裏切ります。

### 3. の重複確認について

転記した Issue の本文には、**必ず出典として本番 Issue の URL を書いてください**
（`{{PROD_SITE_URL}}/issues/<id>`）。次回以降はこれで重複を判定します。

```bash
gh issue search "<本番 Issue の id>" -R {{REPO}} --state all --match body
```

### 4. の「すでに直っていないか」が最も重要です

**利用者の報告は、直った後もそこに残り続けます。** 報告された時点の不具合が、
その後の修正で解消していることがあります。これを見落とすと、**修正ループが
実装済みの機能をもう一度作りにいきます。**

実際にあった例: 「名前を出して投稿したのに匿名扱いされる」という報告があったが、
データ側は最初から正しく（`is_anonymous: false`）、表示側が投稿者名を出せて
いなかっただけだった。報告の 13 時間後にマージされた PR で解消していた。

確認の方法:

- **本番で実際に確かめる。** `curl -s "{{PROD_SITE_URL}}/issues/<id>" | grep ...` で、
  報告された症状が今も出ているかを見る
- **API のデータと画面の表示を分けて見る。** 上の例のように、データは正しいのに
  表示だけが間違っていることがある。逆もある
- 投稿日時と、その後マージされた PR を突き合わせる

直っていた場合は **Issue を作らないでください。** 報告の最後に「◯◯は #XX で解消済み
だったため転記しなかった」と書いてください。本番の Issue を解決済みにする操作は
認証が要るので、人間に委ねます。

### 転記するときの書き方

- **原文を必ず引用する。** 要約で置き換えないでください。利用者の言葉そのものが、
  何に困っているかの一次情報です
- そのうえで、**あなたが確かめた事実を足してください。** 「殺風景」という感想に対して
  「写真を持つ Issue が 8 件中 4 件あるのに一覧に 1 枚も出ていない」を足せば、
  感想が着手できる問題になります
- **感想と、確認した事実を混ぜないでください。** どこまでが利用者の言葉で、
  どこからがあなたの調査かを読み分けられるようにしてください

## 重要な制約

### 上限

**今回作成する Issue は最大 {{MAX_NEW_ISSUES}} 件までです。** それ以上見つけても、最も深刻な {{MAX_NEW_ISSUES}} 件に絞ってください。残りは報告の最後にリストとして書くだけにしてください（次回以降に回されます）。

「深刻」の判断は、**ユーザーから見た影響の大きさ**を基準にしてください。コードとして
気持ち悪いかではありません。**機能が丸ごと使えない**、**画面から到達できない**といった
問題は、内部実装の粗さより優先度が高いです。

### 推測で Issue を立てない

**「〜かもしれない」で Issue を立てないでください。** 実際に確認できたものだけにしてください。

確認の方法は**観点によって異なります**。

#### 「あるコードが壊れている」ことを示す場合

`security` / `test-quality` / `correctness` など、既存コードの欠陥を扱う観点です。

- テストを書いて実際に再現する（確認後は必ず削除する）
- 検証コマンド（{{VERIFY_CMDS_INLINE}}）を実行する
- 該当コードを読んで、その経路が実際に到達可能か確かめる

再現できなかったものは Issue にしないでください。ノイズになります。

#### 「あるべきものが無い」ことを示す場合

`product-gap` / `ux` / `spec-drift` など、**存在しない機能**を扱う観点です。

**この種の問題はテストでは再現できません。**「地図が無い」を再現するテストは書けません。
ここで前節の基準を機械的に当てはめると、**本来最も重要な問題が「確認できないから」という
理由で全て捨てられます。** 実際にそうなっていました。

この場合の「確認」とは、**無いことを具体的に示すこと**です:

- 該当する機能を探した経路を示す（`grep` した語、見たディレクトリ、読んだファイル）
- 呼ばれていないことを示す（例: API のエンドポイントはあるが、`apps/web/src` から
  `fetch` している箇所が0件）
- 画面のどこにも入口が無いことを、実際にコンポーネントを読んで確認する
- CLAUDE.md / README の記述と、実装の対応を1つずつ突き合わせる

「探したが見つからなかった」は**十分な根拠**です。ただし**どう探したかを必ず書いてください**。
探し方が甘くて見落としている可能性を、読む人が判断できるようにするためです。

### コードを変更しない

あなたの仕事は**発見と記録**です。修正は別のループが行います。

一時的に検証用のテストファイルを作るのは構いませんが、**必ず削除してから終了してください**。`git status` で作業ツリーがクリーンであることを確認してください。

### Issue のタイトルには機械可読なキーを付ける

重複判定を安く行うため、タイトルの先頭に `[領域:トピック]` の形式でキーを付けてください。

```
[api/issues.ts:authz] PATCH / DELETE に所有者チェックがない
[web/page.tsx:api-integration] トップページが API を叩いていない
[ci:cache] turbo のキャッシュキーに環境変数が含まれていない
```

領域はファイルパスかコンポーネント名、トピックは問題の性質を表す短い英単語にしてください。

## Issue の書き方

以下を必ず含めてください。

1. **概要** — 何が問題か、1〜2文で
2. **再現手順または該当箇所** — `ファイル:行` で具体的に。再現できたなら実際の出力を貼る
3. **なぜ問題か** — どういう状況で顕在化するか。影響範囲
4. **対応案** — 直し方の方針。判断が必要な点があれば選択肢を示す

**確認したこと・していないことを正直に書いてください。** 「再現テストで確認済み」「コードを読んだ限りそう見えるが未実行」を区別して書いてください。

## Issue の粒度

**「1つ閉じたら実際に問題が解決する」単位にしてください。**

同じ根を持つ問題を別々の Issue に分けないでください。例えば「PATCH に認可がない」と「DELETE に認可がない」は、片方だけ直しても保護にならないので**1つの Issue**にします。

### 同じ土台を必要とする Issue には、それを書く

修正ループは**複数の Issue を並行して解き、互いに何を作っているかを知りません。**
そのため、2つの Issue が同じ土台（ページ、共通関数、テーブル）を必要とすると、
それぞれが独立に同じものを作ります。

実際に起きたこと: 「Issue 詳細ページが無い」「コメント機能が無い」「手伝いますボタンが無い」
の3件を別々に立てた結果、**3つとも独立に `/issues/[id]` のページと `fetchIssue()` を
作りました。** どれも単体では正しく CI も通りましたが、マージの段で衝突しました。

立てようとしている Issue が、既存の Issue と同じ土台を必要とするなら:

- **Issue 本文に「#XX の土台（〜）が前提。先に #XX を解決するのが望ましい」と明記する**
- 土台そのものが未着手なら、**土台を独立した Issue として先に立てる**ことを検討する
  （「詳細ページを作る」を1件にして、コメントや手伝いますボタンはその上に載せる）

これは粒度を細かくしろという意味ではありません。**依存関係を書き残せば、
人間がマージ順を判断できます。** 書かないと、コンフリクトで初めて気付くことになります。

### 判断の重さが違う作業を、1つの Issue に混ぜない

前節とは逆に、**分けるべき場合**です。判断が要る部分と要らない部分が同じ Issue に
入っていると、**判断待ちのあいだ、判断が要らない部分まで止まります。**

実際に起きたこと: 「多言語対応が無い」という Issue には、3つの作業が入っていました。

| 作業 | 判断の重さ |
|---|---|
| UI 文言の外部化（14ファイル・194行） | 軽い（機械的な作業） |
| 言語の切り替え（ja / en） | 軽い |
| **Issue 本文の LLM 翻訳** | **重い**（翻訳タイミング、従量コスト、失敗時の扱い） |

3つ目だけが議論を要するのに、**Issue 全体が `needs-discussion` で止まり、
機械的にやれる194行の外部化にも着手できませんでした。**

書こうとしている Issue に、以下が混ざっていないか確かめてください:

- **すぐ着手できる部分**（やることが決まっている、既存の方針に従うだけ）
- **人間の判断が要る部分**（新規依存の選定、コスト構造が変わる、後戻りしにくい）

混ざっているなら**分けてください。** 分けたうえで、判断が要る側の Issue 本文に
「#XX（すぐ着手できる側）が土台」と書けば、前節の依存関係として繋がります。

判断が要るかどうかの目安:

- 新しい依存パッケージが要る → **要る**
- 使うほど課金される仕組みが入る → **要る**
- 権限・公開範囲・プライバシーが変わる → **要る**（後から戻せない）
- 既存の方針に従って書くだけ → 要らない

## ラベル

作成する Issue には必ず `{{BOT_LABEL}}` ラベルを付けてください。加えて、適切なら以下も付けてください:

- `bug` — 明確な不具合
