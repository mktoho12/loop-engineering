## 手順

### 1. 状態を確認する

```bash
git branch --show-current   # {{BRANCH}} になっているはず
git status                  # クリーンなはず
```

ブランチが違う、または作業ツリーが汚れている場合は、**何もせずにその旨を報告して終了してください**（環境の準備に失敗しています）。

### 2. 修正する前に、問題を再現する

**いきなり直さないでください。** まず問題が実在することを自分で確認してください。

可能なら**失敗するテストを先に書いてください**（Red → Green）。これにより:
- 問題が実在することが証明される
- 修正が効いたことが証明される
- 将来の再発を防げる

再現できない場合は、Issue にその旨をコメントして終了してください。**推測で直さないでください。**

#### 「速さ」や「時刻」に依存するテストを書かない

実行のたびに結果が変わるテストは、**本物の退行と区別が付かなくなります。**
「また例のフレーキーだろう」と流すようになると、本物を見逃します。

実際に起きたこと: `updated_at` が更新で必ず進むことを期待するテストがありましたが、
実装は `strftime(...,'now')`（ミリ秒精度）を入れているだけでした。
処理が1ミリ秒以内に終わると値が変わらず、**6回に1回落ちて**いました。
テストが実装より強い保証を期待していた状態です。

- 「連続して実行すれば値が変わるはず」を前提にしない。
  **保証しているのは実装か、それとも偶然の実行速度か**を確かめてください
- 順序・一意性・単調増加が要るなら、**実装側で保証**してください。
  時計の解像度に頼ると、速いマシンや空いている CI で壊れます
- 落ちるテストを直したときは、**同じテストを5回以上繰り返して**毎回同じ結果に
  なることを確認してください（1回通っただけでは直った証拠になりません）

#### 「手元では通るが CI で落ちる」ときは、まず手元で落ちる形を作る

CI でだけ落ちる問題を、**手元で再現しないまま直そうとしないでください。**
仮説が当たったかどうかを CI でしか確かめられなくなり、1回の試行に
数分〜十数分かかります。しかも外れたときに何が違うのか分かりません。

実際に起きたこと: CI で `Export named 'headers' not found in module 'next/headers'`
が出た。「モックの登録がファイルの実行順に依存しているせいだ」と考えて
preload を入れたが、**原因はそこではなく、CI は同じエラーで落ち続けた。**
CI を1周無駄にしている。

本当の原因は、`mock.module` がモジュール全体を差し替えるため、モックに
書かなかった export（`headers`）が消えていたことだった。依存パッケージが
それを import していたので落ちていた。

手順:

1. **エラーメッセージを額面どおりに読む。** 「`headers` が無い」なら、
   まず本当に無いのかを確かめる。実行順やキャッシュを疑うのはその後
2. **手元で落ちる最小のテストを書く。** 上の例なら
   「モックを読み込んだ後 `next/headers` の `headers` を参照する」だけで落ちた
3. **落ちることを確認してから直す。** 直したら、そのテストが通ることも確認する
4. **そのテストを残す。** 環境差で落ちる問題は忘れた頃に再発します

環境差が絡む問題（OS、実行順、キャッシュ、並列度）は、**手元で再現できた時点で
半分解決しています。** 再現できないまま push するのは、当てずっぽうを
CI に採点させているのと同じです。

### 3. 修正する

- 既存のコードの書き方に合わせてください（命名、エラーハンドリングの形、コメントの密度）
- Issue に書かれた範囲を直してください。**関係ない改善を混ぜないでください**
- 判断が必要な点が Issue に書かれている場合、選んだ理由を PR 本文に書いてください

#### 土台が必要になったら、まず「誰かが作っていないか」を見る

あなたと同時に、別のループが別の Issue を解いています。**互いに何を作っているかを
知りません。** そのため、複数の Issue が同じ土台を必要とすると、それぞれが独立に
同じものを作ります。

実際に起きたこと: Issue #58（詳細ページ）・#60（コメント）・#61（手伝いますボタン）が、
**3つとも独立に `/issues/[id]` のページと `fetchIssue()` を書きました。**
どれも単体では正しく、テストも通り、CI も緑でした。しかしマージの段になって
衝突し、解消に人手が必要になりました。#61 のコードには「#58 が入ったら統合される」
と書かれており、**重複に気付いていたのに避ける手段が無かった**状態でした。

Issue を解くのに新しい土台（ページ、共通関数、テーブル、型）が要ると分かったら、
**作り始める前に**確認してください:

```bash
# 未マージの PR で、同じものを作っていないか
gh pr list -R {{REPO}} --state open --json number,title,headRefName

# 気になる PR があれば、変更ファイルを見る
gh pr view <番号> -R {{REPO}} --json files --jq '.files[].path'
```

見つかったときの対応:

- **既にある PR の方が土台として素直なら、それを取り込む。**
  `git merge origin/<相手のブランチ>` してから、自分の Issue の分を足す。
  PR 本文に「#XX を土台にしている」と書いて、マージ順を人間に伝えてください
- **自分で作る必要があるなら、最小限にする。** 相手が本命の実装を持っているなら、
  自分は動くための最小限だけを作り、PR 本文に
  **「#XX が入ったら統合が必要」と明記**してください
- どちらの場合も、**PR 本文の「既知の未解決事項」に重複の事実を書く**こと。
  黙っていると、マージする人がコンフリクトで初めて気付きます

#### マイグレーションの番号は、追加する直前に確認する

DB のマイグレーションを足すときは、**ファイルを作る直前に**既存の番号を確認してください。

```bash
ls apps/api/migrations/
```

ブランチを切った時点の番号で決め打ちすると、その間に別の PR がマージされて
同じ番号になります。実際に `0004` が2回、`0005` と衝突する形で作られました。
`git merge` はどちらも「新しいファイル」として扱うので**自動では検出されません**。

以下がすべて exit 0 になることを確認してください:


**通らなければ直してください。** 通るまで次に進まないでください。

### 5. ここでコミットして push し、ドラフト PR を出す（レビューの前に）

**レビューに入る前に、必ずコミット・push・PR 作成まで済ませてください。**

```bash
git add -A && git commit -m "（形式は手順7を参照）"
git push -u origin {{BRANCH}}
gh pr create -R {{REPO}} --base {{BASE_BRANCH}} --head {{BRANCH}} --draft \
  --title "（仮）{{ISSUE_TITLE}}" \
  --body "Closes #{{ISSUE_NUM}}

レビュー前の暫定 PR です。手順6のレビューを経て本文を書き直します。"
```

理由は、**実行時間の上限で作業ごと失われるのを防ぐため**です。

実際に起きたこと（その1）: Issue #67 の実行で、実装は完成しテストも全て通っていたのに、
レビューに 167 ターン・37 分を使い切って**コミットに到達しませんでした。**
worktree は破棄され、$18 を消費して成果はゼロ。同じことが4回繰り返され、
**合計 $50 以上が失われました。**

実際に起きたこと（その2）: 2026-08-19 の Issue #143 は、コミットまでは到達したものの
**上限の2秒前（2698秒 / 上限2700秒）で殺され、push に到達しませんでした。**
コミットは worktree の外のブランチに残るので作業自体は失われませんが、
**修正ループはブランチのある Issue をスキップする**ため、その Issue は
人間が気づくまで永久に選ばれなくなります。実際に #139 と #143 の2件が詰まり、
オープン Issue がその2件だけだったため **152 回連続で SKIP** し、
ループは2日間まったく仕事をしませんでした。

**コミットだけでは足りません。push して PR にしてはじめて、
作業が「見える」状態になり、Issue のロックも解けます。**

レビューの指摘は、この PR に追加コミットして反映してください（手順7・8）。

**この時点で機械的検証（手順4）が通っていない状態でコミットしないでください。**
壊れたものを残しても意味がありません。

### 6. 検証する（意味的）— 重要

**ここが最も重要な工程です。**

自分の書いたコードを自分で採点すると甘くなります。**Task ツールで別のエージェントを起動し、レビュアーとして検証させてください。**

レビュアーへの指示には以下を含めてください:

- **日本語で報告すること。作業中の思考も、報告も、すべて日本語。**
  レビュアーは別のエージェントなので、この指示を明示的に渡さないと英語で作業します
  （実際にそうなった実行があります）
- **上限を明示すること。** 「調査は 30 ターン以内、または 15 分以内に収め、
  そこで打ち切って分かった範囲を報告すること」と伝えてください。
  上限を渡さないと、レビュアーは本番環境の調査まで始めて時間を使い切ります
- Issue の内容（何を解決すべきだったか）
- 「あなたはレビュアーであり実装者ではない」こと
- 「テストが通っているから OK で終わらせないこと」
- 以下の観点で能動的に穴を探すこと:
  1. Issue の問題が**本当に**解決されているか
  2. テストが実質的な検証をしているか（通るだけの空テストになっていないか）
  3. **ユニットテストでは検出できない種類の問題**はないか（設定漏れ、経路上の障害物、本番環境固有の問題）
  4. 既存コードとの一貫性
  5. 新たな問題を作り込んでいないか
- **コードを修正せず、指摘だけすること**（一時的に変更して検証するのは構いませんが、必ず元に戻すこと）

**テストの検出力を疑うときは、変異体（mutant）を作って確かめるよう指示してください。**
実装をわざと壊してみて、テストが落ちるかを見る手法です。落ちなければ、そのテストは
その種の欠陥を検出できていません。

このとき、**ステータスコードを変える変異体だけでなく、副作用を変える変異体も試す**よう
指示してください（例:「401 を返すが削除は実行してしまう」）。前者しか試さないと、
テストの検出力を過大評価します。

**変異体は必ず元に戻してください。** 戻し忘れたまま commit すると、
壊れた実装がそのまま PR に乗ります。戻したあとテストが元の件数だけ通ることを
確認してから次に進んでください。

レビュアーの指摘を受けたら:
- **妥当な指摘は直す**。直したら再度 手順4 の機械的検証を回す
- **妥当でないと判断した指摘は、その理由を PR 本文に書く**（黙って無視しない）
- レビュアーが Issue の範囲外の問題を見つけた場合、**直さずに PR 本文に「別途対応が必要」として書く**

### 8. PR を仕上げる

手順5でドラフト PR は既に出ています。ここでは本文を整え、レビュー可能な状態にします。

```bash
git push origin {{BRANCH}}          # 手順7の追加コミットを反映

```


PR 本文には必ず以下を含めてください:

- **`Closes #{{ISSUE_NUM}}`** — Issue が自動でクローズされるように
- **何をしたか** — 修正の内容と、なぜその方針にしたか
- **検証結果** — 4 で実行したコマンドの結果

- **既知の未解決事項** — この PR で直していない関連問題があれば正直に書く

## やってはいけないこと

- **`main` に直接コミットしない**
- **PR を自分でマージしない**（マージは人間が判断します）
- **Issue の範囲外の変更を混ぜない**（見つけたら PR 本文に書くだけ）
- **`git push --force` を使わない**
- **既存のテストを消さない・弱めない**（テストが落ちるなら実装を直す）
- **他人のブランチや PR を触らない**

### 失敗を成功として扱わない

**「取得に失敗した」と「無かった」は違います。** ここを同じ扱いにすると、
静かに間違った動きをし続けます。落ちてくれた方がまだ気付けます。

実際に起きたこと。監視ループにこう書かれていました:

```bash
# 既存の Issue を探す（重複して作らないため）
EXISTING="$(gh issue list ... || echo "null")"
```

`gh` がネットワークの瞬断で失敗すると `"null"` になり、
**「既存の Issue が無い」と解釈して新しい Issue を作りました。**
同じ Issue が4件でき、コメントが188件積まれました。

同じ形の間違いがもう1つありました。「報告済み」を記録する処理で、
**投稿の成否を見ずに記録していた**ため、投稿に失敗した異常が
「報告済み」として二度と報告されなくなる状態でした。

守ること:

- **`|| true` / `|| echo <既定値>` で外部コマンドの失敗を握りつぶさない。**
  握りつぶしてよいのは「失敗しても意味が変わらない」場合だけ
  （例: 既に存在するラベルの作成）
- **「〜した」ことの記録は、実際にできてから書く。**
  先に記録すると、失敗したときに再試行の機会を失う
- 失敗したら**何もせずに終わる**方が、間違った前提で進むより安全。
  終了コードを非ゼロにすれば、次の周期で再試行されます
- API・DB・ファイルの読み書きなど、**自分の外側とやり取りする箇所**は
  すべてこの観点で見直してください

### 終わらないコマンドを書かない

あなたは無人で動いていて、止める人がいません。**待ち続けるコマンドは、実行時間の
上限に達するまでループ全体を占有します。** 実際に、次の1行で 40 分以上を溶かし、
成果ゼロで打ち切られた実行があります:

```bash
# 絶対に書かないこと
until ! pgrep -f opennextjs >/dev/null; do sleep 5; done
```

`pgrep -f opennextjs` は、**このコマンド自身を実行しているシェル**
（`bash -c "...opennextjs..."`）にマッチします。自分がいる限り条件が成立せず、
永久に終わりません。

守ること:

- **`pgrep -f <文字列>` で完了を待たない。** 自分自身にマッチする
- プロセスの終了を待つなら **PID を指定する**（`until ! ps -p 12345 >/dev/null; do sleep 5; done` は安全）
- そもそも**バックグラウンドにせず前景で実行する**のが最も確実。待つ必要がなくなる
- どうしても待つ場合は **`timeout` で上限を付ける**（`timeout 300 <コマンド>`）
- `sleep` の合計が数分を超える設計にしない

## 時間を使いすぎていると感じたら

実行時間には上限があり、超えると**その時点で打ち切られます**。中途半端に
打ち切られるより、成果を残して終わる方が価値があります。

**手順5でコミットしていれば、打ち切られてもブランチは残ります**（worktree は
消えますが、コミットは共有の `.git` に入るため）。ループはコミットのある
ブランチを消さず、ログに手動で PR を作る手順を出します。

ただしこれは保険です。**PR まで出さないと、次の実行は「ブランチが既にある」
として同じ Issue をスキップします。** 自動では先に進みません。

検証（手順6）で以下のような状態になったら、**完璧を目指すのをやめて切り上げてください**:

- 変異体を 3〜4 個試して、いずれもテストが正しく検出できている
- レビュアーの指摘に一通り対応し、残りが軽微なものだけになっている
- **原因が分からないまま**、同じテストを何度も実行して確率的な現象を追いかけている

最後の項目は、手順2の「5回以上繰り返して確認する」と矛盾しません。**原因が分かって
直したなら、5回程度の確認で足ります**（そこで止まらないなら直っていません）。
やめるべきなのは、原因が掴めないまま「今度は通るかもしれない」と回し続けることです。

そのときは、**まずコミットして PR を出してください。** そのうえで、やり残した検証や
残っている疑問を PR 本文の「既知の未解決事項」に書けば、人間が判断できます。
**検証を完璧にすることより、成果を残すことを優先してください。**

## 詰まったとき

以下の場合は、**無理に進めずに Issue にコメントして終了**してください:

- 問題が再現できない
- Issue の内容が曖昧で、複数の解釈があり、どれを選ぶかで結果が大きく変わる
- 修正に大規模な設計変更が必要で、Issue のスコープを超える
- 機械的検証がどうしても通らない
- **新しい依存パッケージの追加が必要**（下記参照）

コメントには「何を試したか」「なぜ進められないか」「何が決まれば進められるか」を書いてください。中途半端な PR を出すより価値があります。

### 新しい依存パッケージが必要になった場合

**`{{PKG_MANAGER}} install` / `{{PKG_MANAGER}} add` は実行せず、Issue にコメントして人間に依頼してください。**

コメントに書くこと:

- どのパッケージが必要か（バージョンも）
- なぜ必要か。標準機能や既存の依存で代替できないか検討した結果も
- どのワークスペースに入れるか（`apps/api` / `apps/web` / `packages/shared` / ルート）

**禁止の理由**: この worktree の `node_modules` は、メインの作業ディレクトリへの
**シンボリックリンク**です。

```
.worktrees/issue-N/node_modules  →  <メインの作業ディレクトリ>/node_modules
```

`{{PKG_MANAGER}} install` を実行すると、リンクの先（＝メインの `node_modules`）を直接書き換えます。
worktree 内での作業のつもりが共有している本体を壊し、**同時に走っている他のループの
足元も崩れます**。隔離が壊れるので実行しないでください。

既存の依存を使うだけなら問題ありません。禁止しているのは**インストールの実行**だけです。
